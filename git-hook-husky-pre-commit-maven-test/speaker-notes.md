# Git Hook(Husky)을 활용한 Commit 전 Maven Test 강제화 상세 대본

발표 파일: [git-hook-husky-pre-commit-maven-test.md](./git-hook-husky-pre-commit-maven-test.md)

## 발표 방향

- 발표 목표: Docker나 Dev Container 같은 공통 개발환경이 부족한 상황에서도, 최소한 commit 시점에는 같은 테스트 명령을 강제하는 방법을 설명한다.
- 핵심 메시지: 완벽한 환경 통일이 어렵다면, `mvnw + Git Hook + Husky`로 commit 전 최소 품질 게이트를 만들 수 있다.
- 최종 구조: `pre-commit -> ./mvnw test`, `CI -> ./mvnw verify`.

---

## 슬라이드 0. 제목

### 상세 대본

"안녕하세요. 오늘은 Git Hook과 Husky를 활용해서 commit 전에 Maven 테스트를 강제하는 방법을 소개하겠습니다.

제목에 Maven Test 강제화라고 되어 있지만, 단순히 Maven 명령어 하나를 실행하는 이야기는 아닙니다.

이번 발표의 핵심은 협업 환경에서 모든 개발자가 최소한 같은 기준으로 코드를 검증하게 만드는 것입니다.

이상적으로는 Docker나 Dev Container처럼 공통 개발환경을 만들어서 JDK 버전, Maven 버전, 실행 명령, OS 차이까지 맞추는 것이 좋습니다.

하지만 모든 프로젝트가 처음부터 그렇게 구성되어 있지는 않습니다. 특히 기존 프로젝트이거나, 교육용/공공 프레임워크 기반 예제처럼 환경이 다양하게 열려 있는 경우에는 개발자마다 로컬 환경이 다를 수 있습니다.

그래서 오늘은 공통 개발환경이 완벽하지 않은 상황에서도 commit 직전에는 최소한 같은 테스트 명령을 실행하게 만드는 방법을 다룹니다."

### 짧게 말하면

"공통 개발환경이 부족한 프로젝트에서 commit 전 테스트를 강제하는 방법을 소개하겠습니다."

## 슬라이드 1. 왜 이 주제인가?

### 상세 대본

"먼저 왜 이 주제를 선택했는지부터 설명하겠습니다.

협업 프로젝트에서 가장 이상적인 방식은 Docker나 Dev Container 같은 공통 실행 환경을 제공하는 것입니다.

공통 실행 환경이 있으면 개발자마다 JDK 버전이 다르거나 Maven 버전이 다르거나, PATH 설정이 달라서 명령어가 안 도는 문제를 줄일 수 있습니다.

예를 들어 어떤 사람은 JDK 17로 실행하고, 어떤 사람은 JDK 21로 실행하거나, 어떤 사람은 시스템에 설치된 Maven으로 실행하고, 어떤 사람은 IDE 내장 Maven으로 실행하면 같은 코드라도 결과가 달라질 수 있습니다.

하지만 현실적으로 모든 프로젝트가 Docker 기반으로 구성되어 있지는 않습니다.

기존 프로젝트일 수도 있고, 팀원이 각자 로컬 환경을 쓰는 상황일 수도 있고, 아직 공통 개발환경을 만들 여력이 없는 단계일 수도 있습니다.

그렇다고 아무 규칙도 없이 각자 알아서 테스트하고 commit하게 두면 협업 품질이 흔들립니다.

그래서 이 발표에서는 환경을 완전히 통일하는 방법이 아니라, 공통 환경이 부족할 때 최소한 commit 전에는 같은 테스트 규칙을 강제하는 방법에 집중합니다."

### 핵심 문장

"Docker 같은 공통 환경이 없더라도, commit 전 테스트 규칙은 만들 수 있습니다."

## 슬라이드 2. 공통 개발환경이 약하면 생기는 문제

### 상세 대본

"공통 개발환경이 잘 갖춰져 있으면 팀원들이 거의 같은 조건에서 코드를 실행합니다.

같은 JDK, 같은 Maven 실행 방식, 같은 테스트 명령, 같은 테스트 결과를 기대할 수 있습니다.

하지만 공통 개발환경이 약하면 개발자마다 검증 방식이 달라집니다.

예를 들어 개발자 A는 `./mvnw test`를 실행하고 commit합니다. 이 경우 프로젝트가 제공하는 Maven Wrapper를 사용하기 때문에 비교적 안정적입니다.

반면 개발자 B는 프로젝트의 Wrapper가 아니라 로컬에 설치된 `mvn test`를 실행합니다. 이때 로컬 Maven 버전, Maven 설정, JDK 버전이 프로젝트 기준과 다르면 다른 결과가 나올 수 있습니다.

개발자 C는 IDE에서 현재 수정한 테스트 몇 개만 실행하고 commit할 수 있습니다. 이 경우 전체 테스트가 깨져도 알지 못할 수 있습니다.

개발자 D는 급해서 테스트를 아예 실행하지 않고 commit할 수도 있습니다.

중요한 점은 Git은 이런 차이를 모른다는 것입니다. Git은 코드가 맞는지, 테스트를 실행했는지 검사하지 않습니다. `git commit` 명령을 실행하면 변경사항을 기록할 뿐입니다.

그러면 문제는 PR이나 CI 단계에서 뒤늦게 드러납니다.

이 발표의 목표는 Docker를 대체하는 것이 아닙니다. Docker가 가능하면 Docker가 더 근본적인 해결책입니다.

하지만 Docker 같은 공통 개발환경이 아직 없다면, 최소한 commit 직전에는 모든 개발자가 같은 명령인 `./mvnw test`를 실행하도록 강제하자는 것이 이 발표의 출발점입니다."

### 핵심 문장

"공통 환경이 없으면 검증 방식이 사람마다 달라지므로, commit 전에 최소한 같은 테스트 명령을 강제해야 합니다."

## 슬라이드 3. 전체 흐름 먼저 보기

### 상세 대본

"전체 흐름을 먼저 보면 구조는 단순합니다.

개발자가 `git commit`을 실행합니다.

그러면 Git은 바로 commit을 만들기 전에 `pre-commit`이라는 Hook을 먼저 실행합니다.

이 Hook은 Husky를 통해 관리됩니다. Husky는 프로젝트 안의 `.husky/pre-commit` 파일을 실행합니다.

그 파일 안에서 `./mvnw test`를 실행합니다.

테스트가 성공하면 commit이 계속 진행됩니다. 테스트가 실패하면 commit이 중단됩니다.

그리고 이 로컬 단계는 빠른 1차 차단 역할입니다. 모든 검증을 로컬 commit 전에 다 넣으면 너무 느려질 수 있습니다.

그래서 더 무거운 검증은 CI에서 `./mvnw verify` 같은 명령으로 처리하는 구성이 좋습니다.

정리하면 로컬에서는 빠르게 막을 수 있는 문제를 먼저 막고, CI에서는 더 강하게 최종 검증을 하는 구조입니다."

### 핵심 문장

"로컬 pre-commit은 빠른 1차 차단, CI는 최종 검증입니다."

---

## 슬라이드 4. Git Hook이란?

### 상세 대본

"이제 Git Hook부터 기초적으로 설명하겠습니다.

Git Hook은 Git에서 특정 이벤트가 발생했을 때 자동으로 실행되는 스크립트입니다.

여기서 이벤트란 commit하기 전, commit 메시지를 작성한 후, push하기 전 같은 Git의 특정 시점을 말합니다.

대표적으로 `pre-commit`, `commit-msg`, `pre-push` 같은 Hook이 있습니다.

이번 발표에서 사용하는 것은 `pre-commit`입니다.

`pre-commit`은 이름 그대로 commit이 만들어지기 직전에 실행됩니다.

흐름은 이렇습니다.

개발자가 `git commit`을 실행하면 Git은 먼저 pre-commit Hook이 있는지 확인합니다.

Hook이 있으면 그 스크립트를 실행합니다.

스크립트가 성공하면 commit을 계속 만들고, 스크립트가 실패하면 commit을 중단합니다.

그래서 pre-commit Hook은 commit 전에 실행되는 품질 게이트로 사용할 수 있습니다."

### 핵심 문장

"pre-commit Hook은 commit 직전에 자동으로 실행되는 스크립트입니다."

---

## 슬라이드 5. Hook은 어떻게 commit을 막나?

### 상세 대본

"그럼 Hook이 commit을 어떻게 막을 수 있는지 설명하겠습니다.

핵심은 종료 코드입니다.

프로그램이나 스크립트는 실행이 끝날 때 운영체제에 종료 코드를 반환합니다.

일반적으로 종료 코드 `0`은 성공을 의미합니다.

반대로 `1` 이상은 실패를 의미합니다.

Git Hook도 이 규칙을 따릅니다.

pre-commit Hook이 종료 코드 0으로 끝나면 Git은 commit을 계속 진행합니다.

하지만 pre-commit Hook이 1 이상의 종료 코드로 끝나면 Git은 commit을 중단합니다.

여기서 Maven 테스트와 연결됩니다.

`./mvnw test`를 실행했을 때 테스트가 모두 성공하면 Maven은 성공 코드 0으로 종료됩니다. 그러면 Hook도 성공하고 commit이 진행됩니다.

반대로 테스트가 하나라도 실패하면 Maven은 실패 코드로 종료됩니다. 그러면 Hook도 실패하고 commit이 중단됩니다.

즉 우리가 직접 Git을 막는 복잡한 로직을 짜는 것이 아니라, Maven 테스트의 성공/실패 결과를 Git Hook의 성공/실패로 연결하는 구조입니다."

### 핵심 문장

"Maven 테스트 실패가 Hook 실패가 되고, Hook 실패가 commit 차단으로 이어집니다."

---

## 슬라이드 6. Husky란?

### 상세 대본

"다음은 Husky입니다.

Git Hook은 Git 자체 기능입니다. 그래서 Husky가 없어도 `.git/hooks` 폴더에 직접 스크립트를 만들면 Hook을 사용할 수 있습니다.

그런데 문제가 있습니다.

`.git/hooks`는 로컬 Git 저장소 내부에 있는 폴더입니다. 보통 Git으로 버전 관리되지 않습니다.

즉 내 컴퓨터의 `.git/hooks/pre-commit`에 스크립트를 만들어도, 다른 팀원이 clone을 받았을 때 그 파일이 자동으로 공유되지 않습니다.

이러면 Hook을 팀 규칙으로 사용하기 어렵습니다.

Husky는 이 문제를 해결하기 위해 많이 사용하는 도구입니다.

Husky를 사용하면 `.husky/pre-commit` 같은 파일을 프로젝트 안에서 관리할 수 있습니다.

그리고 `package.json`에 설정을 두어서 의존성 설치 시 Hook 경로를 초기화할 수 있습니다.

정리하면 Git Hook은 '언제 실행할지'를 담당하고, Maven은 '무엇을 검사할지'를 담당하고, Husky는 그 Hook 규칙을 팀 프로젝트 파일로 관리하게 해주는 역할을 합니다."

### 핵심 문장

"Husky는 Git Hook을 팀원이 공유할 수 있는 프로젝트 규칙으로 만들어주는 도구입니다."

## 슬라이드 7. 왜 `.git/hooks` 대신 Husky인가?

### 상세 대본

"여기서 자연스럽게 이런 질문이 나올 수 있습니다.

그냥 `.git/hooks/pre-commit` 파일을 직접 만들면 안 되나?

가능합니다. 개인 프로젝트이거나, 자기 로컬에서만 쓸 규칙이면 직접 만들어도 됩니다.

하지만 협업 프로젝트에서는 불편합니다.

첫 번째로 `.git/hooks`는 로컬 저장소 내부라 버전 관리가 어렵습니다. 팀원에게 같은 파일이 자동으로 전달되지 않습니다.

두 번째로 프로젝트 규칙이 코드 저장소 안에 명확하게 남지 않습니다. 누가 어떤 Hook을 쓰고 있는지 확인하기 어렵습니다.

세 번째로 새로운 팀원이 clone을 받았을 때 같은 규칙을 재현하기 어렵습니다.

Husky를 사용하면 `.husky/pre-commit` 파일을 프로젝트 내부에 두고 관리할 수 있습니다.

그래서 Hook 실행 자체보다 중요한 것은 Hook을 팀 규칙으로 관리할 수 있다는 점입니다.

이번 예제도 이 관점에서 Husky를 사용합니다."

### 핵심 문장

"Husky의 장점은 Hook을 개인 설정이 아니라 팀 규칙으로 남길 수 있다는 점입니다."

---

## 슬라이드 8. 커밋 전에 무엇을 실행할 것인가?

### 상세 대본

"이제 commit 전에 어떤 Maven 명령을 실행할지 정해야 합니다.

Maven에는 여러 lifecycle 단계가 있습니다. 그중 여기서는 `test`와 `verify`를 비교합니다.

`test`는 주로 단위 테스트를 실행하는 단계입니다. 상대적으로 빠르기 때문에 commit 전에 실행하기 좋습니다.

반면 `verify`는 더 넓은 검증을 포함할 수 있습니다. 통합 테스트, 패키징 이후 검증, 품질 플러그인까지 연결되어 있으면 시간이 더 오래 걸릴 수 있습니다.

commit은 개발자가 자주 하는 작업입니다. 여기에 너무 무거운 검증을 넣으면 개발 흐름이 느려지고, 오히려 Hook을 우회하고 싶어질 수 있습니다.

그래서 저는 pre-commit에는 `./mvnw test`를 추천합니다.

그리고 더 무거운 `./mvnw verify`는 pre-push나 CI에서 실행하는 것이 좋습니다.

즉 로컬 commit 전에는 빠르게 깨지는 테스트를 막고, CI에서는 더 강한 검증을 맡기는 분리 전략입니다."

### 핵심 문장

"pre-commit에는 빠른 `test`, CI에는 더 강한 `verify`가 적합합니다."

---

## 슬라이드 9. 왜 `mvn`이 아니라 `mvnw`인가?

### 상세 대본

"여기서 또 중요한 선택이 있습니다.

왜 `mvn test`가 아니라 `./mvnw test`를 쓰는가입니다.

`mvn`은 내 컴퓨터에 설치된 Maven을 실행합니다.

그러면 개발자마다 Maven 버전이 다를 수 있습니다. 어떤 사람은 최신 Maven을 쓰고, 어떤 사람은 오래된 Maven을 쓸 수 있습니다.

PATH 설정이 잘못되어 있으면 명령 자체가 안 될 수도 있습니다.

반면 `mvnw`는 Maven Wrapper입니다.

Maven Wrapper는 프로젝트가 지정한 Maven 버전을 사용해서 빌드를 실행하게 도와주는 스크립트입니다.

즉 시스템에 설치된 Maven에 덜 의존하고, 프로젝트 기준의 Maven 실행 방식을 제공합니다.

공통 개발환경이 약할수록 이런 차이가 중요합니다.

완벽하게 Docker처럼 모든 것을 통일하지는 못하더라도, 적어도 Maven 실행은 프로젝트 기준에 맞추는 것이 좋습니다.

그래서 Hook에서도 `mvn test`가 아니라 `./mvnw test`를 사용합니다.

Windows에서 직접 실행할 때는 `.\mvnw.cmd test`를 사용하고, Husky의 shell 스크립트 안에서는 `./mvnw test`를 사용합니다."

### 핵심 문장

"공통 환경이 약할수록 로컬 Maven보다 프로젝트의 Maven Wrapper를 쓰는 것이 안전합니다."

## 슬라이드 10. 가장 기본적인 설정 흐름

### 상세 대본

"Husky 설정 흐름은 기본적으로 간단합니다.

먼저 npm으로 Husky를 개발 의존성에 추가합니다.

`npm install --save-dev husky`

그 다음 `npx husky init`을 실행하면 Husky 기본 설정이 만들어집니다.

보통 이 과정에서 `.husky/pre-commit` 파일이 생성되고, `package.json`에 `prepare` 스크립트가 들어갑니다.

`prepare` 스크립트는 npm install 이후 Husky를 초기화하는 용도로 쓰입니다.

이 스크립트가 있어야 팀원이 프로젝트를 clone 받고 의존성을 설치했을 때 Hook 설정도 같이 준비될 수 있습니다.

일반적인 단일 프로젝트에서는 `package.json`에 `"prepare": "husky"` 정도로 설정합니다.

다만 이번 예제는 저장소 루트 안에 여러 발표 예제가 있고, 이 프로젝트가 하위 폴더에 있기 때문에 실제 설정은 조금 다르게 들어갑니다. 그 부분은 다음 슬라이드에서 설명하겠습니다."

### 핵심 문장

"Husky는 npm 의존성과 `prepare` 스크립트로 Hook 초기화를 관리합니다."

## 슬라이드 11. 기본형 Hook 예시

### 상세 대본

"가장 단순한 pre-commit Hook은 이 정도면 됩니다.

맨 위의 `#!/usr/bin/env sh`는 이 파일을 shell 스크립트로 실행하겠다는 의미입니다.

`set -e`는 중간에 실행한 명령이 실패하면 즉시 스크립트를 중단하라는 설정입니다.

그리고 마지막에 `./mvnw test`를 실행합니다.

이 구조에서는 테스트가 성공하면 스크립트가 정상 종료되고 commit이 진행됩니다.

테스트가 실패하면 `set -e` 때문에 스크립트가 실패로 끝나고 commit이 중단됩니다.

이 예시는 개념 설명용으로 가장 단순합니다.

실무에서는 메시지를 더 친절하게 출력하거나, 하위 모듈로 이동하거나, 특정 조건에서만 실행하도록 조정할 수 있습니다.

하지만 핵심은 변하지 않습니다. commit 전에 `./mvnw test`가 성공해야 commit이 가능하다는 것입니다."

### 핵심 문장

"기본형 Hook의 핵심은 `set -e`와 `./mvnw test`입니다."

## 슬라이드 12. 이 프로젝트의 Husky 설정

`package.json`에는 Husky 의존성과 prepare 스크립트가 들어 있습니다.

여기서 `private: true`는 이 패키지를 npm에 배포하지 않겠다는 의미입니다. 이 프로젝트는 Node 애플리케이션이 아니라 Husky 설정을 위해 package.json을 사용하는 것이기 때문에 private로 두는 것이 자연스럽습니다.

중요한 부분은 `prepare` 스크립트입니다.

그래서 `cd .. && husky git-hook-husky-pre-commit-maven-test/.husky`처럼 한 단계 위로 올라가서 Husky 경로를 지정합니다.

발표에서 이 부분은 너무 깊게 들어갈 필요는 없지만, 질문이 나오면 '일반 프로젝트는 prepare: husky면 되고, 이 예제는 하위 폴더라 경로를 지정했다'고 설명하면 됩니다."

### 핵심 문장

"일반 프로젝트는 `prepare: husky`, 이 예제는 하위 폴더라 Husky 경로를 직접 지정했습니다."

## 슬라이드 13. 이 프로젝트의 pre-commit Hook

### 상세 대본

"이제 실제 pre-commit Hook 파일을 보겠습니다.

파일 위치는 `.husky/pre-commit`입니다.

첫 줄은 shell 스크립트 실행을 위한 선언입니다.

`set -e`는 실패 시 즉시 종료하기 위한 설정입니다.

그 다음 `echo`로 commit 전에 Maven 테스트를 실행한다는 메시지를 출력합니다. 이 메시지는 시연할 때 중요합니다. commit을 눌렀을 때 Hook이 실제로 실행되고 있다는 것을 눈으로 확인할 수 있기 때문입니다.

그 다음 `cd git-hook-husky-pre-commit-maven-test`로 예제 프로젝트 폴더로 이동합니다.

왜 이동하냐면 Git 저장소 루트는 `egov-vscode2026`이고, Maven 프로젝트의 `pom.xml`은 그 하위 폴더에 있기 때문입니다.

마지막으로 `./mvnw test`를 실행합니다.

정리하면 commit 직전에 예제 프로젝트 폴더로 이동해서 Maven Wrapper로 테스트를 실행하는 구조입니다.

테스트가 성공하면 Hook이 성공하고 commit이 진행됩니다.

테스트가 실패하면 Hook이 실패하고 commit이 중단됩니다."

### 핵심 문장

"이 파일이 실제 commit 전 테스트 강제 규칙입니다."

## 슬라이드 14. 시연 시나리오

### 상세 대본

"시연은 일부러 아주 단순한 예제를 사용합니다.

서비스 코드는 이름 검증 로직입니다.

규칙은 이름이 null이거나 길이가 2자 미만이면 예외를 던지는 것입니다.

즉 한 글자 이름인 `A`는 허용되지 않아야 합니다.

테스트 코드에서는 `validateName("A")`를 실행했을 때 `IllegalArgumentException`이 발생해야 한다고 검증합니다.

현재 정상 코드에서는 `name.length() < 2`이므로 `A`가 들어오면 예외가 발생합니다. 그래서 테스트가 통과합니다.

시연에서는 이 조건을 일부러 `name.length() < 1`로 바꿉니다.

그러면 `A`는 길이가 1이기 때문에 더 이상 예외가 발생하지 않습니다.

하지만 테스트는 여전히 `A`가 예외를 던져야 한다고 기대합니다.

그래서 테스트가 실패합니다.

그리고 이 실패를 가진 상태로 commit을 시도하면 pre-commit Hook이 `./mvnw test`를 실행하고, 테스트 실패 때문에 commit을 막는 것을 보여줄 수 있습니다."

### 핵심 문장

"서비스 로직을 일부러 잘못 바꿔서, 테스트 실패가 commit 차단으로 이어지는 것을 보여줍니다."

## 슬라이드 15. 실패 시연 방법

### 상세 대본

"이제 실제 실패 시연 순서입니다.

먼저 정상 상태에서 테스트가 통과하는 것을 보여줍니다.

PowerShell에서 예제 프로젝트 폴더로 이동한 뒤 `.\mvnw.cmd test`를 실행합니다.

Windows PowerShell에서는 `mvnw.cmd`를 실행하고, shell 스크립트 안에서는 `./mvnw`를 실행한다고 설명하면 됩니다.

정상 상태라면 테스트 2개가 모두 통과하고 `BUILD SUCCESS`가 나옵니다.

그 다음 서비스 코드를 일부러 잘못 수정합니다.

원래 조건은 `name.length() < 2`입니다.

이걸 `name.length() < 1`로 바꿉니다.

이제 한 글자 이름인 `A`는 예외가 나지 않게 됩니다. 하지만 테스트는 예외가 나야 한다고 기대하므로 실패할 준비가 된 상태입니다.

그 다음 Git 저장소 루트로 이동합니다.

이 부분이 중요합니다. commit은 Maven 프로젝트 폴더가 아니라 Git 저장소 루트인 `egov-vscode2026`에서 시연합니다.

변경한 Java 파일을 `git add`로 stage에 올립니다.

그리고 `git commit -m "test: pre-commit hook demo"`를 실행합니다.

이때 Git은 바로 commit을 만들지 않고 pre-commit Hook을 실행합니다.

콘솔에 `[Husky] Commit 전 Maven 테스트를 실행합니다.`라는 메시지가 나오면 Hook이 실행된 것입니다.

그 후 Maven 테스트가 실패하고 `BUILD FAILURE`가 나오면 commit이 중단됩니다.

이 장면에서 강조할 점은 테스트가 실패했다는 사실보다, 실패한 테스트를 가진 변경사항이 commit되지 못했다는 점입니다."

### 시연 중 말할 문장

"지금은 일부러 서비스 로직을 잘못 바꾼 상태입니다. commit을 시도하면 Git이 바로 commit하지 않고, Husky pre-commit Hook을 먼저 실행합니다. Hook 안에서 Maven 테스트가 실패하므로 commit이 중단됩니다."

## 슬라이드 16. 성공 시연 방법

### 상세 대본

"다음은 성공 시연입니다.

실패 시연 후에는 서비스 코드를 다시 정상으로 되돌립니다.

조건을 다시 `name.length() < 2`로 바꿉니다.

이제 한 글자 이름 `A`는 다시 예외를 던지므로 테스트 기대값과 코드가 일치합니다.

다시 예제 프로젝트 폴더에서 `.\mvnw.cmd test`를 실행하면 `BUILD SUCCESS`가 나옵니다.

그 다음 Git 저장소 루트로 이동해서 같은 방식으로 `git add`, `git commit`을 실행합니다.

이번에도 pre-commit Hook은 실행됩니다.

다만 이번에는 `./mvnw test`가 성공하므로 Hook도 성공하고 commit이 정상 진행됩니다.

여기서 강조할 점은 같은 commit 명령을 실행했는데도, 테스트 성공 여부에 따라 결과가 달라진다는 것입니다.

테스트 실패 상태에서는 commit이 막히고, 테스트 성공 상태에서는 commit이 진행됩니다.

이게 바로 commit 전 품질 게이트입니다."

### 시연 중 말할 문장

"같은 commit 명령이지만 이번에는 테스트가 통과합니다. 그래서 Hook도 성공하고 commit이 만들어집니다."

## 슬라이드 17. 한계와 트러블슈팅

### 상세 대본

"마지막으로 이 방식의 한계도 같이 봐야 합니다.

첫 번째, Hook이 아예 안 도는 경우가 있습니다. 이때는 `.husky/pre-commit` 파일이 제대로 있는지, Git의 `core.hooksPath`가 올바르게 잡혀 있는지 확인해야 합니다.

두 번째, GUI 도구에서만 `command not found`가 나는 경우가 있습니다. 터미널에서는 되는데 GUI Git 클라이언트에서는 PATH가 다르게 잡히는 경우가 있기 때문입니다. 이 경우 Node, Git Bash, Java, Maven 경로 초기화 문제를 확인해야 합니다.

세 번째, commit이 너무 느려질 수 있습니다. 그래서 pre-commit에 너무 무거운 검증을 넣는 것은 조심해야 합니다. 빠른 단위 테스트는 pre-commit에 두고, 더 무거운 검증은 CI나 pre-push로 나누는 것이 좋습니다.

네 번째, 테스트를 skip하는 옵션이 있을 수 있습니다. 예를 들어 `skipTests`나 `maven.test.skip=true` 같은 설정이 잘못 들어가면 Hook이 있어도 테스트가 실제로 실행되지 않을 수 있습니다.

다섯 번째, `git commit --no-verify`를 사용하면 Hook을 우회할 수 있습니다.

그래서 Hook만으로 협업 품질이 완성되는 것은 아닙니다.

Hook은 로컬에서 빠르게 실수를 줄이는 장치이고, 최종적으로는 CI와 Branch Protection까지 연결해야 합니다."

### 핵심 문장

"Hook은 좋은 1차 방어선이지만, 최종 품질 게이트는 CI와 Branch Protection까지 함께 가야 합니다."

## 슬라이드 18. 그래서 제 추천안은

### 상세 대본

"정리하겠습니다.

공통 개발환경이 약한 프로젝트일수록 로컬에 설치된 `mvn`보다 프로젝트의 `mvnw`를 우선 사용하는 것이 좋습니다.

commit 전에는 너무 무겁지 않은 `./mvnw test`를 실행해서 기본 테스트 실패를 빠르게 막습니다.

더 무거운 검증은 CI에서 `./mvnw verify`로 처리합니다.

Git Hook은 commit 직전에 테스트를 실행하는 시점을 담당합니다.

Husky는 그 Hook을 팀 프로젝트 안에서 관리할 수 있게 해줍니다.

다만 Hook은 우회할 수 있으므로 Hook만 믿으면 안 됩니다. CI와 Branch Protection까지 같이 연결해야 실제 협업 품질을 유지할 수 있습니다.

이 발표의 핵심은 테스트를 개인의 습관에만 맡기지 말자는 것입니다.

공통 개발환경이 완벽하지 않더라도, commit 전에는 최소한 같은 명령을 실행하게 만드는 것. 이것이 `mvnw + Husky + pre-commit test` 조합의 목적입니다."

### 마무리 멘트

"오늘 발표에서 말씀드리고 싶었던 핵심은, 모든 프로젝트가 Docker처럼 완벽한 공통 환경을 갖추고 있지는 않다는 점입니다.

그럴수록 실행 환경 자체를 단번에 통일하기보다, 최소한 commit 시점에는 같은 테스트 명령을 강제하는 것이 현실적인 출발점이 될 수 있습니다.

그래서 Maven 기반 프로젝트에서는 `mvnw + Husky + pre-commit test + CI verify` 조합을 추천드립니다. 감사합니다."

## 발표 중 질문 대비

### Q. Docker가 있으면 Husky가 필요 없나요?

"Docker나 Dev Container가 있으면 실행 환경 통일에는 훨씬 좋습니다. 하지만 Docker가 있어도 commit 전에 테스트를 자동 실행하는 규칙은 별도로 유용합니다. Docker는 환경을 맞추는 도구이고, Hook은 commit 시점에 검사를 강제하는 도구라 역할이 다릅니다."

### Q. `git commit --no-verify`로 우회할 수 있지 않나요?

"맞습니다. 그래서 Hook만으로는 최종 품질을 보장할 수 없습니다. Hook은 로컬에서 빠르게 실수를 줄이는 장치이고, 최종 검증은 CI와 Branch Protection으로 막아야 합니다."

### Q. 왜 pre-commit에 `verify`를 넣지 않나요?

"`verify`는 더 넓은 검증을 포함할 수 있어서 느려질 수 있습니다. commit은 자주 하는 작업이라 너무 느리면 개발 흐름이 나빠집니다. 그래서 pre-commit에는 빠른 `test`, CI에는 더 강한 `verify`를 권장합니다."

### Q. Java 프로젝트인데 왜 npm과 package.json이 나오나요?

"Husky가 Node 생태계에서 많이 쓰이는 Git Hook 관리 도구이기 때문입니다. 이 프로젝트에서 package.json은 애플리케이션 실행용이 아니라 Husky 설치와 Hook 초기화를 관리하기 위한 파일입니다."
