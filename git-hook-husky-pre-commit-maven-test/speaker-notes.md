# Git Hook(Husky)을 활용한 Commit 전 Maven Test 강제화

발표 파일: [git-hook-husky-pre-commit-maven-test.md](./git-hook-husky-pre-commit-maven-test.md)

## 발표 흐름

- 발표 시간 기준: 약 6~8분
- 목표: Docker 같은 공통 환경이 없는 프로젝트에서, 최소한 commit 시점의 품질 규칙을 만드는 방법을 설명
- 핵심 메시지: `mvnw + Husky + pre-commit test + CI verify`

---

## 슬라이드 1. 제목

### 발표 멘트 예시

"안녕하세요. 오늘은 Git Hook과 Husky를 활용해서 commit 전에 Maven 테스트를 강제하는 방법을 소개하겠습니다.  
제가 이 주제를 고른 이유는, 빌드 도구 자체를 설명하는 것보다 협업 품질을 실제로 높일 수 있는 방식이 더 실용적이라고 봤기 때문입니다."

---

## 슬라이드 2. 왜 이 주제인가?

### 발표 멘트 예시

"보통은 Docker 같은 공통 실행 환경으로 버전과 실행 조건을 맞추는 게 가장 이상적입니다.  
하지만 모든 프로젝트가 그렇게 구성되어 있지는 않습니다.  
공통 환경이 없으면 JDK, Maven, PATH, OS 차이 때문에 같은 코드를 받아도 어떤 사람은 실행되고 어떤 사람은 실행되지 않는 문제가 생깁니다.  
그래서 저는 환경을 완전히 통일하는 이야기보다, 공통 환경이 부족한 프로젝트에서 최소한의 품질 규칙을 만드는 방법에 집중했습니다."

---

## 슬라이드 3. 실제로 어떤 문제가 생기나?

### 발표 멘트 예시

"로컬에서는 `git add`, `git commit`만 치면 너무 쉽게 commit이 됩니다.  
문제는 이 전에 `mvn test`를 안 돌렸을 때입니다.  
이 실패는 보통 PR의 CI에서 늦게 터지거나, 더 나쁘면 merge 이후 main 브랜치에서 드러납니다.  
즉 테스트는 하면 좋은 일이 아니라, 실제 협업에서는 강제되어야 하는 일에 가깝습니다."

---

## 슬라이드 4. 역할 분리

### 발표 멘트 예시

"여기서 역할을 분리해서 보면 더 명확합니다.  
Maven이나 Gradle은 빌드와 테스트를 실제로 실행하는 도구입니다.  
Git Hook은 특정 Git 시점에 스크립트를 강제 실행하는 장치입니다.  
그리고 Husky는 그 Hook을 프로젝트 규칙으로 관리하기 쉽게 해주는 도구입니다.  
정리하면 Maven은 무엇을 검사할지, Hook은 언제 검사할지, Husky는 그 규칙을 어떻게 팀 전체가 같이 쓸지를 담당합니다."

---

## 슬라이드 5. 추천 구조

### 발표 멘트 예시

"제가 추천하는 기본 구조는 간단합니다.  
개발자가 commit을 시도하면 Husky의 pre-commit이 먼저 실행되고, 여기서 `./mvnw test`를 돌립니다.  
성공하면 commit이 진행되고, 실패하면 commit이 중단됩니다.  
그리고 CI에서는 더 무거운 `./mvnw verify`를 돌려서 최종 검증을 맡깁니다.  
즉 로컬은 빠른 1차 차단, CI는 최종 품질 게이트라고 보시면 됩니다."

---

## 슬라이드 6. test vs verify

### 발표 멘트 예시

"Maven에서 commit 전에 무엇을 실행할지도 구분이 필요합니다.  
`test`는 단위 테스트 중심이라 빠르고, pre-commit에 넣기 적합합니다.  
반면 `verify`는 더 넓은 검증 단계까지 포함할 수 있어서 무거워질 수 있습니다.  
그래서 제 추천은 pre-commit에는 `./mvnw test`, 그리고 pre-push나 CI에서는 `./mvnw verify`입니다."

---

## 슬라이드 7. 왜 mvnw인가?

### 발표 멘트 예시

"여기서 중요한 게 `mvn`이 아니라 `mvnw`를 쓰는 이유입니다.  
개발자마다 Maven 버전이 다를 수 있고, PATH 설정도 다를 수 있습니다.  
특히 공통 환경이 없는 프로젝트일수록 이 차이가 더 크게 드러납니다.  
그래서 Maven Wrapper를 쓰면 프로젝트가 요구하는 버전으로 실행하게 만들 수 있고, Hook에서도 같은 실행 경로를 쓸 수 있습니다."

---

## 슬라이드 8. 왜 Husky인가?

### 발표 멘트 예시

"Git 자체 훅만 써도 되지 않느냐는 질문이 자주 나옵니다.  
가능은 하지만 `.git/hooks`는 로컬 저장소 내부라 버전 관리가 불편합니다.  
Husky는 `.husky/` 디렉터리를 프로젝트 안에서 관리하게 해주기 때문에, clone 받은 팀원도 같은 규칙을 비교적 쉽게 재현할 수 있습니다.  
그래서 Husky의 핵심은 Hook 실행 자체보다 Hook을 팀 규칙으로 관리하는 방식에 있습니다."

---

## 슬라이드 9. 기본 설정

### 발표 멘트 예시

"설정 흐름은 비교적 단순합니다.  
`npm install --save-dev husky` 후에 `npx husky init`을 실행하면 `.husky/pre-commit`이 만들어지고, `package.json`에 `prepare` 스크립트가 반영됩니다.  
이 `prepare`가 있어야 팀원이 의존성 설치 후 Hook 초기화까지 같이 따라가기 쉽습니다."

---

## 슬라이드 10. 실무형 예시

### 발표 멘트 예시

"발표용으로는 기본형보다 이 실무형 예시가 더 좋습니다.  
루트에서 Husky를 관리하고, 같은 폴더에 있는 Spring Boot Maven 프로젝트에 대해 바로 `./mvnw test`를 실행합니다.  
성공하면 commit이 진행되고, 실패하면 commit이 중단된다는 메시지를 콘솔에 명확히 남깁니다.  
이렇게 해야 발표 시연에서도 흐름이 잘 보입니다."

---

## 슬라이드 11. 시연 시나리오

### 발표 멘트 예시

"시연에서는 이름 검증처럼 아주 단순한 도메인을 쓰는 게 좋습니다.  
예를 들어 이름은 2자 이상이어야 한다는 규칙을 두고, 테스트에서는 한 글자 이름이 예외를 던져야 한다고 검증합니다.  
여기서 서비스 코드를 일부러 잘못 바꿔서 한 글자 이름도 통과하게 만들면, 테스트가 실패하고 Hook이 commit을 막습니다.  
핵심은 테스트가 실패하는 것보다, 실패한 테스트를 들고 commit하지 못하게 만든다는 점입니다."

---

## 슬라이드 12. 한계와 트러블슈팅

### 발표 멘트 예시

"물론 이 방식이 만능은 아닙니다.  
훅이 아예 안 도는 경우에는 파일명이나 `core.hooksPath`를 확인해야 합니다.  
GUI에서만 `command not found`가 나는 경우는 PATH 초기화 문제일 수 있습니다.  
또 commit이 너무 느리면 로컬에서는 `test`, CI에서는 `verify`로 나누는 게 좋습니다.  
그리고 `skipTests` 설정이나 `--no-verify` 우회 가능성도 있기 때문에, Hook만으로 끝내면 안 됩니다."

---

## 슬라이드 13. 최종 추천안

### 발표 멘트 예시

"제가 조사해본 기준으로 가장 현실적인 추천안은 이렇습니다.  
공통 환경이 약한 프로젝트일수록 `mvnw`를 우선 사용하고, pre-commit에는 `./mvnw test`를 둡니다.  
더 무거운 검증은 CI의 `./mvnw verify`에 맡기고, Husky로 Hook을 프로젝트 규칙으로 관리합니다.  
그리고 최종적으로는 CI와 Branch Protection까지 연결해야 협업 품질이 완성됩니다.  
한 줄로 요약하면 테스트를 습관이 아니라 규칙으로 바꾸는 것이 핵심입니다."

---

## 마무리 멘트

"오늘 발표에서 말씀드리고 싶었던 핵심은, 모든 프로젝트가 Docker처럼 완벽한 공통 환경을 갖추고 있지는 않다는 점입니다.  
그럴수록 실행 환경 자체를 단번에 통일하기보다, 최소한 commit 시점에는 같은 테스트를 강제 실행하도록 만드는 것이 더 현실적인 출발점이 될 수 있습니다.  
그래서 저는 Maven 기반 프로젝트에서는 `mvnw + Husky + pre-commit test + CI verify` 조합을 추천드립니다. 감사합니다."
